## 1. Contexto & Problema Arquitetural

1. **Necessidade da Biblioteca Mercado Pago (`mercadopago.php`)**:
   - O Stripe não oferece parcelamento no cartão no Brasil (`available_plans: []`). O ecossistema precisa suportar o **Mercado Pago** (Checkout Bricks / Card Payment Brick, Pix, Boleto e Reembolsos) como cidadão de primeira classe no Core, espelhando o rigor de `stripe.php` e `paypal.php`.
2. **Acoplamento Hardcoded em `plataforma-gateways.php` e nos Módulos**:
   - Hoje, `gestor/controladores/plataforma-gateways/plataforma-gateways.php` possui um `switch ($gateway)` fixo em `paypal` e `stripe`, com funções específicas (`plataforma_gateways_stripe_webhook()`, `plataforma_gateways_paypal_webhook()`) e payloads heterogêneos enviados aos módulos.
   - Consequentemente, cada módulo consumidor (`orders`, `subscriptions`, etc.) precisa conhecer detalhes internos de assinatura de cabeçalhos, formato de JSON e máquina de estados de cada provedor (`Stripe-Signature` vs headers do PayPal vs `x-signature` do Mercado Pago), espalhando condicionais `if ($tipo === 'stripe') / elseif ($tipo === 'paypal')` por milhares de linhas.
3. **Visão do Engenheiro Chefe Humano (Plug-and-Play)**:
   - Construir no Core uma **Interface / Contrato Universal de Gateways (`gestor/bibliotecas/pagamentos-gateways.php`)** e transformar `plataforma-gateways.php` numa ponte agnóstica.
   - Qualquer gateway ativo (`stripe`, `mercadopago`, `paypal` ou futuros provedores) implementa o mesmo contrato de operações (configurar, testar conexão, declarar capacidades, iniciar pagamento, sincronizar estado autenticado, reembolsar e validar/normalizar webhooks).
   - O controlador `plataforma-gateways.php` valida/normaliza o evento pela ponte do driver e entrega aos módulos um **Envelope Canônico de Pagamento** (preservando os campos brutos para retrocompatibilidade total com código legado).

## 2. Escopo Técnico Detalhado

### Frente 1 — Biblioteca Oficial `gestor/bibliotecas/mercadopago.php`
Criar a biblioteca REST do Mercado Pago (`https://api.mercadopago.com`) seguindo os padrões de `stripe.php` e `paypal.php`:
1. **Convenção de Credenciais (`gateways_pagamentos`, `tipo = 'mercadopago'`)**:
   - `client_id` ➔ **Public Key** (`TEST-...` ou `APP_USR-...`)
   - `client_secret` ➔ **Access Token** (`TEST-...` ou `APP_USR-...`)
   - `webhook_secret` ➔ **Assinatura Secreta do Webhook** (chave secreta configurada em Webhooks no painel Mercado Pago Developers)
   - `configuracoes` (JSON) ➔ `mercadopago.installments` (`enabled`, `max_installments` 1..12, `interest_payer` = `'buyer'|'merchant'`), `mercadopago.render_mode` (`'auto'|'button_first'`).
2. **Funções Obrigatórias de `mercadopago.php`**:
   - `mercadopago_gateways_pagamentos_configurar($params = false)`: carrega do banco por `id` ou pelo gateway ativo de maior prioridade (`ORDER BY prioridade ASC, padrao DESC, id_gateways_pagamentos ASC`).
   - `mercadopago_obter_credenciais()`, `mercadopago_is_modo_gateway()`, `mercadopago_obter_gateway_id()`, `mercadopago_obter_gateway_dados()`.
   - `mercadopago_requisicao($params)`: cliente HTTP cURL seguro com header `Authorization: Bearer <access_token>`, `X-Idempotency-Key` automático em chamadas `POST`, timeout configurável e log em `log_disco(..., 'mercadopago')`.
   - `mercadopago_testar_conexao()`: valida as credenciais chamando `GET /v1/payment_methods` (ou `/users/me`) e confere coerência entre o prefixo da chave (`TEST-` vs `APP_USR-`) e o ambiente (`S` vs `P`) quando aplicável.
   - `mercadopago_criar_pagamento($params)`: `POST /v1/payments` para cartão tokenizado pelo Brick (`token`, `transaction_amount`, `installments`, `payment_method_id`, `issuer_id`, `payer`, `external_reference`, `description`, `metadata`, `notification_url`) ou Pix (`payment_method_id = 'pix'`) ou Boleto.
   - `mercadopago_consultar_pagamento($params)`: `GET /v1/payments/{id}`.
   - `mercadopago_reembolsar($params)`: `POST /v1/payments/{id}/refunds` (total quando sem `amount`, parcial quando `amount` informado).
   - `mercadopago_validar_webhook($params)`: valida o header `x-signature` (`ts=...,v1=...`) + `x-request-id` + `data.id` via HMAC-SHA256 com o `webhook_secret` conforme especificação oficial do Mercado Pago (`id:[data.id];request-id:[x-request-id];ts:[ts];`).
   - `mercadopago_traduzir_status($status)`: mapeia estados do Mercado Pago (`approved`, `pending`, `authorized`, `in_process`, `in_mediation`, `rejected`, `cancelled`, `refunded`, `charged_back`) para os estados canônicos do Conn2Flow.

### Frente 2 — Interface Universal Plug-and-Play (`gestor/bibliotecas/pagamentos-gateways.php`)
Criar a camada de abstração de gateways no Core que unifica todos os provedores:
1. **Registro de Drivers (`pagamentos_gateways_drivers()`)**:
   - Drivers nativos registrados para `stripe`, `mercadopago` e `paypal`, além de permitir extensão via `hook_apply_filters('pagamentos', 'gateways.drivers', $drivers)`.
2. **Consulta Ordenada por Prioridade e Capacidades**:
   - `pagamentos_gateways_listar_ativos($filtros = [])`: consulta `gateways_pagamentos` onde `status = 'A'`, ordenando por `COALESCE(prioridade, 100) ASC, CASE WHEN padrao='S' THEN 0 ELSE 1 END ASC, id_gateways_pagamentos ASC` (com fallback automático caso a coluna `prioridade` ainda não exista no banco de uma instalação antes da migration).
   - `pagamentos_gateway_capacidades($gatewayRow)`: retorna estrutura padronizada:
     ```php
     [
         'tipo' => 'stripe'|'mercadopago'|'paypal',
         'supports_installments' => bool, // false no Stripe BR; configurável no Mercado Pago (default true) e no PayPal (default false)
         'max_installments' => int,       // 1..12
         'interest_payer' => 'buyer'|'merchant',
         'supports_one_time' => bool,     // true em todos
         'supports_recurring' => bool,    // true em stripe e paypal
         'supports_pix' => bool,          // true em mercadopago (e stripe se configurado)
         'render_mode' => 'auto'|'button_first', // lido de configuracoes.render_mode (default 'auto')
         'priority' => int,               // lido de prioridade (default 100)
     ]
     ```
3. **Operações Unificadas do Contrato**:
   - `pagamentos_gateway_configurar($gatewayIdOrRow)`
   - `pagamentos_gateway_testar($gatewayRow)`
   - `pagamentos_gateway_iniciar_cobranca($gatewayRow, $contexto)`
   - `pagamentos_gateway_sincronizar($gatewayRow, $contexto)` ➔ retorna sempre o contrato canônico:
     ```php
     [
         'ok' => bool,
         'canonical_status' => 'awaiting'|'processing'|'paid'|'failed'|'refunded'|'partially_refunded'|'cancelled',
         'gateway_type' => string,
         'gateway_id' => string,
         'gateway_payment_id' => string,
         'gateway_order_id' => ?string,
         'gateway_subscription_id' => ?string,
         'amount' => float,
         'currency' => string,
         'installments' => int,
         'refunded_amount' => ?float,
         'reference' => ?string,
         'raw' => array,
         'error' => ?string,
     ]
     ```
   - `pagamentos_gateway_reembolsar($gatewayRow, $contexto)`
   - `pagamentos_gateway_dashboard_url($gatewayRow, $paymentId)`
   - `pagamentos_gateway_validar_e_normalizar_webhook($gatewayType, $rawBody, $headers, $query = [], $gatewayIdHint = null)`:
     - Localiza os gateways ativos daquele `$gatewayType` (ordenados por compatibilidade de ambiente/prioridade), valida a assinatura (quando o provedor assina) e devolve o **Envelope Canônico de Webhook**:
       ```php
       [
           'valid' => bool,
           'gateway_type' => 'stripe'|'mercadopago'|'paypal',
           'gateway_id' => ?string,
           'event_id' => ?string,
           'event_type' => string, // tipo bruto do provedor
           'canonical_event' => 'payment.paid'|'payment.processing'|'payment.failed'|'payment.refunded'|'payment.partially_refunded'|'payment.cancelled'|'subscription.updated'|'subscription.cancelled'|'subscription.payment_succeeded'|'subscription.payment_failed'|'other',
           'reference' => ?string, // ex: ecommerce:261110-ABCDEF ou subId:payKey
           'gateway_payment_id' => ?string,
           'gateway_order_id' => ?string,
           'gateway_subscription_id' => ?string,
           'resource' => array,
           'event_data' => array,
       ]
       ```

### Frente 3 — Ponte Agnóstica em `gestor/controladores/plataforma-gateways/plataforma-gateways.php`
1. Incluir `'mercadopago'` na lista de gateways conhecidos (`$known_gateways`) — ou consultar dinamicamente `pagamentos_gateways_drivers()`.
2. Adicionar handler universal de webhook/retorno que atende `mercadopago`, `stripe`, `paypal` e qualquer driver futuro registrado em `pagamentos-gateways.php`.
3. Ao disparar `plataforma_gateways_disparar_hook($gateway, $action, $data, $modulo_id)`, injetar a chave `'canonical'` (gerada por `pagamentos_gateway_validar_e_normalizar_webhook` ou pelo normalizador do driver) ao lado dos campos legados (`event_type`, `resource`, `event_data`, `needs_validation`, `raw_body`, `raw_headers`, `signature_header`, `query_string`).
4. Garantir que módulos já existentes continuem funcionando sem quebra e que módulos atualizados (`orders`, `subscriptions`) possam consumir diretamente `$params['data']['canonical']` de forma 100% agnóstica ao gateway.
