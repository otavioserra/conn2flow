# req-166: Resiliência do Transporte SSH/rsync no Windows contra Falha de Descritores dup() no MSYS2 (BATCH-171)

## 1. Descrição do Problema & Contexto

Durante a execução do pipeline `./c2f project:update-all snapphoton-local --confirmar-remoto` no Windows, o estágio 1/8 (Sincronização Core -> Projeto) falha com o seguinte erro retornado pelo `rsync`:

```console
[2026-09-17 15:41:05] Running: rsync -avu -e ssh -o BatchMode=yes -o ConnectTimeout=15 -p 22 --rsync-path sudo rsync --exclude .git/ --exclude /logs/ --exclude /temp/ --exclude resources.map.php /c/Users/otavi/OneDrive/Documentos/GIT/conn2flow/gestor/ otavio@lab.conn2flow.local:/home/snapphoton/web/snapphoton.local/conn2flow-gestor/
 ✖ ERROR  dup() in/out/err failed
rsync: connection unexpectedly closed (0 bytes received so far) [sender]
rsync error: error in rsync protocol data stream (code 12) at io.c(232) [sender=3.4.1]
```

### Causa Raiz Mapeada
1. O pipeline PHP (`c2f project:update-all`) dispara scripts shell através de `proc_open` (`BaseProcessCommand::runShell`), que estabelece pipes anônimos do Win32 para stdin, stdout e stderr.
2. O script Bash resultante (`sync-core-to-project.sh`) invoca o binário `rsync.exe` (MSYS2/Git Bash 3.4.1), que precisa gerar um subprocesso `ssh` via flag `-e`.
3. Ao tentar clonar/duplicar os descritores de arquivo padrão para conectar os pipes com o processo `ssh`, a camada de compatibilidade POSIX do MSYS2/Cygwin falha com `dup() in/out/err failed` devido à ausência de PTY ou inconsistência nos handles herdados da cadeia `PHP (proc_open) -> bash -> rsync -> ssh`.
4. É necessário blindar a execução do `rsync` no Windows/MSYS2 dentro da biblioteca de transporte (`project-transport.sh`), garantindo descritores válidos, suporte a `--blocking-io` ou alternativas de redirecionamento de transporte.
