## 1. Contexto e Justificativa

Durante a validação real no Lab (`conn2flow.local`) em 2026-11-23, foi comprovada a causa raiz do erro `401 Unauthorized use of live credentials (code: 7)` retornado pela API do Mercado Pago:

- As novas aplicações de **Checkout Transparente** criadas no painel do Mercado Pago Developers utilizam a **Orders API v1 (`/v1/orders`)** (campo *Tipo de API: API de Orders*).
- Para essas aplicações, a rota legada `POST /v1/payments` retorna `x-api-server-segment: legacy` + `401 Unauthorized use of live credentials (code: 7)` mesmo com credenciais de teste válidas (`TESTUSER2456402839622594817`) e comprador de teste (`@testuser.com`).
- Sonda real executada em 2026-11-23 no Lab contra `POST https://api.mercadopago.com/v1/orders` com o mesmo token retornou **`HTTP 201 Created`** (`ORDTST01M851JCA32683WCG3XHNR66G4` / `PAY01M851JCAJEXV5YNS5GXA51FG2`), gerando o pagamento e o QR Code Pix do sandbox com sucesso.

O Engenheiro Chefe Humano decidiu manter a aplicação na **API de Orders** (padrão oficial moderno do Mercado Pago) e atualizar a integração do Core (`mercadopago.php`, `pagamentos-gateways.php` e `plataforma-gateways.php`) para operar nativamente com `/v1/orders`.

## 2. Objetivos e Escopo

### Frente 1 — Cliente REST `gestor/bibliotecas/mercadopago.php` na Orders API v1
1. **Criação de pagamento (`POST /v1/orders`):**
   - Adaptar `mercadopago_criar_pagamento()` (mantendo a assinatura/contrato de retorno esperado por `pagamentos-gateways.php`, `ecommerce-payments.php` e `subscriptions`) para montar e enviar o payload da Orders API v1:
     - `type: "online"`, `processing_mode: "automatic"`, `total_amount` (string decimal com 2 casas, ex.: `"1999.00"`), `external_reference`, `description` (se aplicável), `payer` (`email`, `identification`, `first_name`/`last_name`), `transactions.payments[0]` (`amount`, `payment_method`: `id`, `type` [`credit_card`, `debit_card`, `bank_transfer` para Pix, `ticket` para boleto], `token` e `installments` para cartão).
     - Cabeçalho `X-Idempotency-Key` preservado.
   - Normalizar a resposta da Order (`id` da Order `ORD...`, `transactions.payments[0].id` `PAY...`, `status` [`processed`, `action_required`, `failed`, `canceled`, `refunded`, `partially_refunded`], `status_detail`, e dados de Pix: `payment_method.qr_code`, `qr_code_base64`, `ticket_url`, `date_of_expiration`) para o contrato canônico já consumido pelo site!
2. **Consulta / Sincronização (`GET /v1/orders/{id}`):**
   - Adaptar `mercadopago_buscar_pagamento()` (ou `mercadopago_buscar_ordem()`): se o ID começar com `ORD` (Orders API v1), consultar `GET /v1/orders/{id}` e normalizar status/valor/moeda/`external_reference`; manter fallback para `GET /v1/payments/{id}` caso receba ID numérico legado.
3. **Reembolso (`POST /v1/orders/{id}/refund`):**
   - Adaptar `mercadopago_reembolsar()` para reembolso total e parcial via `POST /v1/orders/{id}/refund` (com `transactions` para reembolso parcial quando valor informado), mantendo fallback legado `/v1/payments/{id}/refunds` para IDs numéricos.
4. **Mapeamento de Status Canônicos:**
   - Garantir que todos os status da Orders API v1 (`processed` ➔ `paid`, `action_required` / `in_process` / `created` ➔ `pending`, `failed` / `rejected` ➔ `failed`, `canceled` / `expired` ➔ `cancelled`, `refunded` / `partially_refunded` ➔ `refunded`) sejam traduzidos corretamente em `mercadopago_status_canonico()`.

### Frente 2 — Webhooks de Orders (`mercadopago.php` + `plataforma-gateways.php`)
1. Suportar eventos de webhook da Orders API (`type = "order"` / `action = "order.processed"`, `"order.failed"`, `"order.canceled"`, `"order.refunded"`, etc.) além de `type = "payment"`.
2. Validar a assinatura HMAC `x-signature` conforme o manifesto oficial da Orders API (incluindo `data.id` alfanumérico `ORD...` em minúsculas conforme especificação do Mercado Pago) e consultar `GET /v1/orders/{id}` para montar o envelope canônico entregue aos módulos (`orders` e `subscriptions`).

### Frente 3 — Testes Automatizados & Validação Real no Lab
1. Atualizar `tests/Unit/PHP/MercadoPagoLibraryTest.php` e `tests/Unit/PHP/PagamentosGatewaysInterfaceTest.php` cobrindo payloads/respostas reais da Orders API v1 (cartão parcelado, Pix com QR Code, status canônicos, consulta, reembolso total/parcial e webhook `order.*` com HMAC).
2. Validar no Lab (`conn2flow.local` — usando a branch de integração `lab/req-149-156` no site para não sobrescrever Pagamentos!) com teste real de criação de pagamento **Pix** e **Cartão Parcelado** via `POST /v1/orders` usando o gateway `mercado-pago-sandbox` já configurado.
3. Confirmar compatibilidade com o checkout do `conn2flow-site` (se o Brick precisar de algum ajuste mínimo de `payment_method.type` no `ecommerce-payments.php` / `subscriptions.php`, documentar ou ajustar coordenadamente).
