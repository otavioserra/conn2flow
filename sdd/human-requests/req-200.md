## Diretriz do Humano (2026-09-30)

A recuperação usa **a mesma operação de diff e decisão** do deploy: para cada arquivo diferente, ver o diff e escolher sobrescrever, manter ou mesclar ("esse sim, esse não"). Vale no nível de projeto e no nível do core. O motor é o da [req-199](req-199.md), comum a subir e descer; **não criar um fluxo de decisão paralelo**.

## Itens

1. **Inventário no servidor** — endpoint `POST /_api/project/files` (nome livre, documentar):
   - compara o disco com os manifestos de cada camada e devolve, por arquivo: `camada`, `caminho`, `estado` (`editado`: hash do disco ≠ manifesto; `ausente`: no manifesto e fora do disco; `fora-do-manifesto`: arquivo no disco que nenhuma camada entregou, fora das pastas protegidas de `INSTALACAO_PASTAS_FORA`), `hash_disco`, `hash_manifesto`;
   - filtros: `camadas` (padrão todas), `caminhos` (prefixos), `estados`;
   - com `baixar: true` e uma lista de caminhos, devolve um ZIP com esses arquivos (como o `recover` faz com os dados); nunca sai nada de `autenticacoes/`, `.env`, `logs/`, `backups/`, `temp/`.
   - Autenticado (`api_authenticate`), leitura pura (sem trava de deploy).
2. **Descida no CLI** — `c2f project:recover-files <projeto>` (nome livre, documentar), com `--simular` (padrão), `--aplicar`, `--camada=projeto|core|plugin:<id>`, `--json`:
   - baixa o inventário e os arquivos diferentes para `temp/recover-files/<projeto>/<execução>/`;
   - para a camada **projeto**, compara com o repositório local do projeto (`gestorPath` do `ProjectEnvironmentResolver`):
     - local igual ao que o projeto entregou (hash do manifesto) → a versão do servidor pode ser aplicada direto (com `--aplicar`);
     - local também mudou → **choque de descida**, decidido com o mesmo motor (sobrescrever o local com a do servidor, manter o local, mesclar), reaproveitando `instalacao_choque_acoes/resolver` e as regras (se for preciso um parâmetro novo no motor — por exemplo, a cópia fora da base —, acrescentar sem quebrar os chamadores atuais e cobrir com teste);
   - para a camada **core** (e plugins): só baixa para análise e lista (o core não é aplicado num repositório de projeto); a decisão sobre esse arquivo no servidor já existe pelo `update:resolve`.
   - `--json` para a extensão do VS Code (mesmo padrão de `update:conflicts --json`).
3. **Registro:** as descidas decididas ficam anotadas (arquivo JSON por execução em `temp/recover-files/.../relatorio.json` basta; não criar tabela nova no servidor para a descida).
4. **Docs** (pt-br e en, contrato de frontmatter; `docs:audit` sem aviso nos arquivos tocados): referência da API de projeto, CLI (família do comando) e o conceito de atualizações.

## Critérios de aceite

1. Um arquivo do **projeto** editado direto no servidor aparece no inventário como `editado`; com `--aplicar`, desce para o repositório local quando o local está intacto; quando o local também mudou, vira choque de descida e as três decisões funcionam.
2. Um arquivo do **core** editado no servidor aparece no inventário e é baixado para análise, sem tocar o repositório local.
3. Nada sensível sai pelo ZIP (teste automatizado cobrindo `.env`, `autenticacoes/`, `logs/`, `backups/`, `temp/`, `..`).
4. PHPUnit verde nos testes novos e nos do lote da req-198/199 (`--filter 'UpdateConflicts|UpdateRollback|AtualizacoesManifesto|InstalacaoManifesto|AtualizacoesSistemaTrava|DeployLock|MigrationChecker'`); homologação no tenant isolado.
